# 실행 기록 수정

할 일 아래에 저장된 실행 기록마다 ‘실행 기록 수정’ 버튼이 있습니다. 서울 시간 기준으로 기존 시작·종료 시각, 막힌 이유, 실제로 한 일을 불러와 고칠 수 있습니다. 시각을 바꾸면 실제 분을 다시 계산하고 돌아보기와 내보내기에 반영합니다. 실행 기록 ID와 최초 생성 시각, 할 일의 예상 시간과 완료 상태는 유지합니다.

실제로 하지 않았다면 ‘하지 않았어요 · 0분으로 기록’을 선택하고 날짜와 사유를 적습니다. 미실행 기록은 0분으로 표시하고 완료로 바꾸지 않습니다. 기술적으로 기존 NOT NULL 시각 열에는 해당 날짜의 서울 자정 값을 시작·종료에 동일하게 저장합니다. 이는 날짜 표시용 값이며 실제 작업 시각이 아닙니다. 이 규칙은 `contracts/pds-schema-v2.json`에도 적었습니다. 기존 표와 ID는 유지하므로 DB 구조 마이그레이션은 없습니다.

## 저장 경로

`app/execution-log.tsx`가 기존 값을 불러오고 `POST /api/executions`로 보냅니다. 새 기록은 requestKey, 수정은 id와 previous 필드를 사용합니다. `app/api/executions/route.ts`는 소유권 확인을 거친 할 일에 실행 기록 ID가 실제로 연결돼 있는지 확인합니다. 기존 값이 다른 화면에서 바뀌면 409로 거절해 덮어쓰지 않습니다. 같은 할 일의 같은 시작·종료 시간대가 이미 있어도 409입니다. 날짜·시각 입력은 수행한 경우 1분 이상 7일 이내, 미실행은 같은 시각·0분·사유 필수로 구분합니다.

수정은 실행 기록의 값만 바꾸며 원래 계획이나 완료 이력을 새로 만들지 않습니다. 별도의 실행 수정 이력 표는 추가하지 않았습니다. 여러 날짜에 걸친 같은 할 일을 수정해도 돌아보기는 기존대로 그 할 일의 실행 시간 전체를 합산하므로, 5일 실험의 일별 지표는 실제 실행 날짜별로 구분해 계산해야 합니다.

## 검증

로컬 빌드에서 `node scripts/test-execution-edit.mjs`를 실행했습니다. 검증 계정으로 날짜 변경과 30→45분 재계산, 잘못 입력한 1분→미실행 0분 정정, ID·생성 시각·기록 수 유지, 원래 계획·할 일·완료 수 유지, 돌아보기·내보내기 반영을 확인했습니다. 다른 계정의 할 일 ID 또는 다른 계정의 실행 ID를 섞으면 404, 비로그인은 401, 예전 값을 이용한 덮어쓰기와 시간대 중복은 409, 역전된 시간과 명시하지 않은 0분은 400이었습니다. [검증 결과](execution-edit-tests.json)에 비밀번호·쿠키 없이 남겼습니다.

로컬 Wrangler 프리뷰에서는 익명 POST 직후 다음 요청이 ‘worker restarted mid-request’로 실패하는 현상이 있었습니다. 익명 요청을 마지막에 실행해 해당 요청의 401과 나머지 기능을 각각 확인했습니다. 기존 인증 코드를 바꾸어 우회하지 않았습니다. 운영 환경 확인 결과는 별도 증거 파일로 보관합니다.

운영 배포 뒤 같은 검증 스크립트를 공개 앱 주소에 실행해 전 항목 PASS를 확인했습니다. [운영 검증 결과](execution-edit-production-tests.json)에 따로 보관했습니다. 검증은 별도 QA 계정에서 수행했고, 본인 자료의 정정은 확인받은 날짜와 미실행 여부만 로그인된 화면에서 처리했습니다.
