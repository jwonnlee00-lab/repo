# 과제 7 카드 1 — 인증 선택과 확인

과제 6의 플랜두씨 다이어리에 이메일·비밀번호 가입과 로그인을 붙였습니다. 자료 화면을 열기 전에 세션을 확인하고, 자료 API에서는 요청한 계획의 소유자를 확인합니다. 로그인한 계정의 계획만 목록·돌아보기·내보내기에 포함합니다.

## 선택

분류는 인증 라이브러리이며 Better Auth **1.7.11**과 `@better-auth/drizzle-adapter` **1.7.11**을 사용합니다. 기존 Cloudflare D1·Drizzle 데이터베이스를 유지하면서 비밀번호 해싱과 세션 쿠키 처리를 검증된 라이브러리에 맡길 수 있어 선택했습니다. 버전은 package.json과 package-lock.json에 고정했습니다.

대안으로 Sites의 ChatGPT 인증 서비스를 검토했습니다. 기존 호스팅의 인증 통합은 유지하지만, 과제에서 요구하는 앱 내부 이메일 가입과 비밀번호 오류 안내를 직접 확인하기 어려워 이 카드의 주 방식으로 선택하지 않았습니다. 비밀번호·쿠키를 직접 설계하는 방법도 검토했으나 직접 책임져야 할 보안 범위가 커 선택하지 않았습니다.

공식 참고: [Better Auth 이메일·비밀번호](https://better-auth.com/docs/authentication/email-password), [Drizzle 어댑터](https://better-auth.com/docs/adapters/drizzle), [세션](https://better-auth.com/docs/concepts/session-management).

## 바꾼 소스

- `lib/auth.ts`: Better Auth 설정과 D1 어댑터, 비밀번호 12~128자, 서버 세션 7일. 세션 쿠키 캐시를 끄고 요청마다 서버 세션을 확인합니다.
- `worker/index.ts`: 비로그인 화면 요청은 `/login`으로 302 이동하며 자료 API는 401을 반환합니다. 허용한 인증 엔드포인트만 노출하고, 잘못된 비밀번호와 없는 이메일의 로그인 오류를 같은 401·같은 문장으로 바꿉니다. 인증 응답에서 세션 토큰을 JSON으로 반환하지 않습니다.
- `lib/access.ts`: 요청별 사용자 컨텍스트와 계획·할 일 소유권 검사. 다른 계정의 ID로 접근하면 404를 반환합니다.
- `app/api/entries`, `review`, `export`: 현재 계정의 자료만 조회하고 새 계획에는 서버가 소유자 ID를 붙입니다. 내보내기에 인증 테이블·비밀번호 해시·세션은 넣지 않습니다.
- `app/auth-form.tsx`, `login`, `signup`, `account-bar.tsx`: 가입·로그인·로그아웃 화면입니다. 비밀번호는 화면 상태에만 두고 로그인 성공 후 비웁니다.
- `db/schema.ts`, `drizzle/0007_outgoing_black_queen.sql`: 인증 표와 계획 소유자, 기존 자료 이전 기록을 추가합니다. 소유자만 옮길 때 계획 버전·원본 이력은 바꾸지 않습니다.
- `lib/migration-operator.ts`: 운영용 무작위 비밀값과 대상 사용자 ID를 함께 검사하는 기존 자료 이전 통로입니다. 가입 이메일만으로 이전하지 않습니다. 이전 후 운영용 비밀값을 제거합니다.

## 막히는 장면

`card1-requests.json`은 로컬 빌드의 실제 요청·응답입니다. 비밀번호·쿠키·세션 토큰은 기록하지 않았습니다.

```http
GET /
Cookie: (없음)

HTTP 302
Location: /login
```

```http
GET /api/entries
Cookie: (없음)

HTTP 401
{"error":"로그인이 필요합니다."}
```

```http
GET /api/tasks?planId=[계정A의 계획ID]
Cookie: [계정B 세션, 생략]

HTTP 404
{"error":"자료를 찾을 수 없습니다."}
```

없는 이메일과 올바른 이메일의 틀린 비밀번호로 각각 요청하면 모두 아래 응답입니다.

```http
POST /api/auth/sign-in/email
Content-Type: application/json
{"email":"[검증 이메일]","password":"[기록하지 않음]"}

HTTP 401
{"error":"이메일 또는 비밀번호가 올바르지 않습니다."}
```

가입한 이메일의 대소문자만 바꿔 다시 가입해도 거절됐습니다. 올바른 정보로 로그인한 뒤 로그아웃하면 이전 쿠키를 다시 보내도 자료 API가 401을 반환했습니다. 계정B의 내보내기에는 계정A의 자료나 인증 표가 없었습니다.

## 기존 자료 이전

이전 대상 이메일은 운영 환경의 비밀값으로 지정합니다. 본인이 가입 완료를 확인한 뒤 대상 계정 ID를 확인하고, 미소유 상태인 과제 6 계획에만 소유자를 붙입니다. 할 일·실행·이력은 기존 계획 ID로 연결돼 있어 ID·날짜·내용·시간 단위를 유지합니다. 첫 가입자가 기존 자료를 차지하지 않도록 자동 이전하지 않습니다. 실제 이전 완료 여부와 전후 건수는 가입 확인 후 별도 기록합니다.

## 한계

현재 이메일 소유권 확인 메일과 비밀번호 재설정, MFA는 구현하지 않았습니다. 중복 이메일을 이용한 가입 시도는 거절하지만 가입 오류로 이메일 등록 여부를 추측할 여지는 있습니다. 로그인 오류 문장은 두 경우를 구별하지 않습니다. 분산 환경의 강한 요청 제한과 운영 모니터링은 추가 확인이 필요합니다.

과제 6에서 이미 공개한 자료와 당시 Git 커밋·다운로드 사본의 공개 이력은 이번 로그인으로 회수하지 못합니다. 현재 공개 정적 ZIP과 실제 자료를 넣는 seed 스크립트는 제거했지만 과거 Git 기록은 남아 있습니다. 과거에 공개했던 자료를 처음부터 비공개였던 자료처럼 설명하지 않습니다.

5일 실제 사용과 3일차 전 규칙 변경은 아직 수행하지 않았습니다. 이 문서는 카드 1의 구현·검증 기록이며 5일 사용 완료 기록이 아닙니다.

## 본인 계정 이전 결과

2026년 10월 20일 본인의 가입 완료 답변을 받은 뒤 운영 도구로 대상 가입 계정을 확인했습니다. 이전 요청은 HTTP 200과 `{"migrated":true,"count":7}`을 반환했습니다. 기존 계획 7개의 소유자만 해당 계정으로 지정했으며, 연결된 자료의 ID·날짜·시간 값은 변경하지 않았습니다. 본인 로그인 화면에서 이전 결과를 직접 확인한 기록은 아직 없습니다.

이전 후 운영 환경에서 `LEGACY_MIGRATION_SECRET`을 제거하고 환경 리비전 2로 재배포했습니다. 비로그인 요청을 다시 보냈을 때 `/`는 HTTP 302와 `Location: /login`, `/api/entries`와 `/api/export`는 HTTP 401과 `{"error":"로그인이 필요합니다."}`, `/api/admin/migrate`는 HTTP 404를 반환했습니다. 이전 기능은 비활성 상태입니다.

운영 주소에서 수행한 가입·로그인·로그아웃, 중복 이메일, 서로 다른 계정의 자료 격리 검증은 [운영 요청·응답 기록](card1-production-requests.json)에 있습니다. 비밀번호와 쿠키는 기록하지 않았습니다.
