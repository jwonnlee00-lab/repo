# 카드 3 — 로그인 상태와 세션 종료

이 앱은 Better Auth 1.7.11의 **서버 데이터베이스 세션**으로 로그인한 사람을 알아봅니다. 브라우저에는 서명된 세션 식별 쿠키를 발급하고, 서버는 쿠키를 검증한 뒤 D1 `auth_session`의 사용자와 만료 시각을 확인합니다. 자료 API에 JWT를 URL로 전달하는 방식은 사용하지 않습니다. 쿠키 이름에 token이 들어가지만 이 앱의 인증 방식은 서버 세션입니다.

## 실제 요청 두 개 비교

2026년 10월 20일 운영 주소에서 별도의 검증 계정을 만들었습니다. 자료가 없는 계정이라 로그인 중의 계획 목록은 빈 배열입니다. 성공과 실패의 차이를 명확히 보려고 로그인 때 발급한 쿠키를 변수에 보관한 후, 로그아웃 응답이 쿠키를 지우더라도 변수는 바꾸지 않고 다시 요청했습니다. 비밀번호와 쿠키 원문은 파일이나 출력에 저장하지 않았습니다.

| 항목 | 로그인 중 | 로그아웃 뒤 원래 쿠키 재전송 |
| --- | --- | --- |
| 주소 | `https://plan-do-see-diary-six.jwonnlee00.chatgpt.site/api/entries` | 동일 |
| 방식 | `GET` | 동일 |
| Origin | 사이트의 HTTPS origin | 동일 |
| Cookie | `__Secure-better-auth.session_token=[SAME_SESSION_REDACTED]` | 원래 값과 동일 |
| 상태 | HTTP 200 | HTTP 401 |
| 응답 본문 | `[]` | `{"error":"로그인이 필요합니다."}` |

두 요청 사이에는 같은 쿠키로 `POST /api/auth/sign-out`을 한 번 보냈고 HTTP 200을 받았습니다. 대상 주소·메서드·쿠키·Origin은 바꾸지 않았습니다. 서버에서 로그아웃이 처리됐다는 점만 달라졌습니다. 이후 같은 쿠키의 `/api/auth/get-session` 응답도 `{"user":null}`이었습니다.

실제 [가린 요청·응답 기록](card3-session.json)과 실행 코드 `scripts/test-session.mjs`를 함께 보관했습니다. 운영 DB의 `auth_session` 전체 8행을 읽은 결과에도 방금 로그아웃한 검증 계정의 세션은 0건이었습니다. [DB 확인 결과](card3-db-session.json)에는 계정 ID와 건수만 적고 세션 값과 다른 사용자의 행은 제외했습니다. 브라우저 쿠키만 지운 것이 아니라 서버 세션이 끊겼음을 응답과 DB 양쪽에서 확인한 결과입니다.

## 만료와 연장

`lib/auth.ts`의 `makeAuth()`에 다음 설정이 있습니다.

```ts
session: {
  expiresIn: 60 * 60 * 24 * 7,
  updateAge: 60 * 60 * 24,
  cookieCache: {enabled: false}
}
```

발급 후 만료까지는 604800초, 즉 7일입니다. 운영 DB의 검증 계정 세션 하나에서 생성 시각 `2026-10-20T07:20:47.875Z`, 만료 시각 `2026-10-27T07:20:47.875Z`를 확인했고, 차이는 정확히 604800초였습니다. 서울 시간으로는 각각 10월 20일과 27일 오후 4시 20분 47.875초입니다. 만료는 UTC epoch 밀리초로 저장합니다.

발급 또는 갱신 뒤 하루가 지나 사용하면 현재 시각 기준 7일 뒤로 연장합니다. 따라서 계속 사용하는 세션을 최초 로그인에서 무조건 7일 뒤 끊는 설정은 아닙니다. 사용하지 않아 갱신되지 않으면 저장된 만료 시각에 끝나고, 로그아웃하면 그보다 먼저 즉시 끊깁니다. 운영 발급 쿠키의 `Max-Age=604800`도 검사했습니다. 실제로 7일을 기다리는 시험이나 하루 뒤 연장 시험은 아직 하지 않았고, 설정·저장 시각·쿠키 수명 확인과 로그아웃 즉시 차단 시험을 수행했습니다. [Better Auth 세션 문서](https://better-auth.com/docs/concepts/session-management)의 만료·갱신 설명과도 대조했습니다.

## 쿠키와 비밀키

운영 응답에서 세션 쿠키의 `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`를 확인했습니다. 쿠키 값은 URL의 경로나 쿼리에 넣지 않고 Cookie 헤더로 보냅니다. `app/auth-form.tsx`는 로그인 후 `/`로 이동하며, `app/account-bar.tsx`의 로그아웃도 URL에 세션을 붙이지 않습니다. 성공 응답은 `worker/index.ts`에서 사용자 ID·이메일·이름과 ok 값으로 제한하므로 JSON 응답에 세션 토큰을 반환하지 않습니다. HttpOnly 쿠키는 앱의 JavaScript에서 직접 읽는 용도로 쓰지 않습니다.

서명 비밀키 `BETTER_AUTH_SECRET`은 Sites 운영 환경의 secret으로 보관하고 `lib/auth.ts`에서 서버 환경값으로 읽습니다. 클라이언트용 환경변수나 `.openai/hosting.json`에 원문을 넣지 않았습니다.

[비밀키 원문 검사 결과](card3-exact-secret-scan.json)는 운영 비밀키를 메모리에서만 전달해 소스·브라우저와 서버의 로컬 배포 빌드·문서·스크립트·도달 가능한 전체 Git blob 안에 같은 바이트가 있는지 검사한 결과입니다. 키는 명령행 인자·파일·출력에 기록하지 않았습니다. 일반 비밀키 패턴 검사도 별도로 통과했고 [패턴 검사 결과](card3-secret-pattern-scan.json)를 보관했습니다. 검사 범위는 로컬의 실제 배포용 빌드와 조회 가능한 Git 기록이며, 호스팅 업체 내부 산출물이나 삭제된 도달 불가능 Git 객체까지 검사했다는 뜻은 아닙니다.

## 종료 범위와 재현

T07-C114의 로그아웃 경로에서는 이전 세션이 재사용되지 않는 것을 확인했습니다. 현재 앱에는 비밀번호 변경·재설정 기능이 없으므로 비밀번호 변경 시 다른 세션까지 끊기는 시험은 수행하지 않았습니다. 이번 카드에서 구현하지 않은 기능을 완료한 것으로 기록하지 않습니다.

PowerShell에서 다음 명령으로 같은 검증을 재현합니다. 실행할 때마다 별도의 검증 계정이 생기고 시험 끝에 그 세션을 로그아웃합니다. 실제 사용자의 세션은 건드리지 않습니다.

```powershell
$env:AUTH_TEST_URL='https://plan-do-see-diary-six.jwonnlee00.chatgpt.site'
node scripts/test-session.mjs
```

200 → 로그아웃 200 → 원래 쿠키로 401이 모두 확인되면 PASS가 출력되고 `outputs/evidence/task07/card3-session.json`에 가린 기록이 생깁니다. 통과하지 않으면 assertion 오류로 종료합니다. 제출할 때는 가린 JSON을 사용하고 원본 Cookie, Set-Cookie, HAR는 첨부하지 않습니다.
