# 플랜두씨 다이어리

계획, 실제로 한 일, 돌아본 점을 한 기록에 남기는 공개 다이어리입니다. 돌아보기의 다음 계획을 새 계획으로 옮길 수 있고, 집계 숫자를 누르면 계산에 포함된 기록을 볼 수 있습니다. 기록은 Cloudflare D1 서버 데이터베이스에 저장합니다. 브라우저 저장소에 기록을 보관하지 않습니다.

## 사용 방법

첫 화면의 `새 계획`에서 날짜, 할 일, 예상 시간을 입력합니다. 실행 후 `수정`을 열어 실제로 한 일과 시간을 적고, 돌아본 점과 다음 계획을 남깁니다. 하지 않은 일은 실제 시간을 0분으로 기록하고, 아직 기록하지 않은 일은 빈칸으로 둡니다.

첫 화면에는 로그인이 없다는 안내가 표시됩니다. 링크를 아는 누구나 기록을 읽고 추가·수정·삭제할 수 있으므로 공개 가능한 내용만 사용해야 합니다. 로그인과 개인별 접근 제한은 구현하지 않았습니다.

## 실행 방법

Node.js 22.13 이상에서 `npm ci`로 의존성을 설치하고 `npm run db:generate`로 스키마 변경에 대한 SQL을 생성합니다. 이미 들어 있는 마이그레이션은 변경하지 않습니다. `npm run build`로 빌드한 뒤 아래 명령으로 로컬 DB를 준비합니다.

```sh
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_colorful_zombie.sql
npm start
```

`npm run dev`는 개발 서버를 실행합니다. 로컬과 배포 서버의 DB는 별개입니다. Sites 배포는 `.openai/hosting.json`의 DB 바인딩과 `drizzle/` 마이그레이션을 사용합니다. 새 프로젝트로 배포할 때는 자신의 Sites 프로젝트 ID를 사용해야 합니다.

## 주요 파일

`app/page.tsx`는 계획·실행·돌아보기 입력과 집계별 필터를 제공합니다. `app/api/entries/route.ts`는 GET으로 기록을 읽고 POST로 저장·수정하며 DELETE로 삭제합니다. 날짜, 문자열 길이, 0~1440분의 실제 시간과 1~1440분의 예상 시간을 서버에서 검사합니다. 실제 기록을 작성할 때는 한 일과 실제 시간이 함께 필요합니다.

`db/schema.ts`는 기록 테이블을 정의합니다. `parent`에는 다음 계획을 만들게 된 이전 기록 ID를 저장합니다. SQL은 Drizzle의 매개변수 바인딩을 사용하며, 사용자 입력은 React 텍스트로 표시합니다. HTML로 삽입하지 않습니다. 실행에 필요한 비밀값을 클라이언트나 소스에 넣지 않습니다.

## 검증 결과

2026-10-20 로컬 빌드와 TypeScript 검사를 통과했습니다. `node scripts/test-api.mjs`는 음수 예상 시간, 존재하지 않는 날짜, 실제 시간 없는 실행 기록이 400으로 거절되는지 확인합니다. 실제 0분 기록의 저장·재조회, 수정, 삭제도 확인했습니다. 이 스크립트는 `qa-record`라는 테스트 전용 ID를 사용하므로 로컬 검증에만 사용하세요.

브라우저에서 사용자 제공 팟캐스트 기록을 새로고침 후 확인했고, 시간 차이 집계 1건을 누르면 10월 19일 기록 한 건만 표시됐습니다. 공개 배포 후 확인 결과는 `SUBMISSION.md`에 추가합니다.

## 카드 1: 계획과 이력

계획에는 ID, 시작일·종료일, 우선순위, 성공 기준, 예상 시간이 저장됩니다. 팟캐스트 계획은 당일 기간, 우선순위 보통, 성공 기준 ‘한 편 끝까지 시청하기’, 예상 시간 30분으로 설정했습니다. 우선순위 보통은 초기 설정이며 수정할 수 있습니다.

`최초 계획 · 수정 이력 보기`에서 처음 저장한 내용과 각 저장 버전을 볼 수 있습니다. SQLite 트리거가 기록 저장과 같은 트랜잭션에서 이력 스냅샷을 남깁니다. 기존 기록은 새 항목이 미설정으로 남아 있고, 처음 수정할 때 수정 전 원본을 먼저 보관합니다. 이후 입력한 기간이나 성공 기준을 최초 계획에 소급해 넣지 않습니다. 보관 시각은 스냅샷을 보관한 시각입니다.

동시에 열린 화면에서 오래된 버전으로 저장하면 409 오류를 표시하고 입력을 유지합니다. 삭제하면 해당 계획과 이력도 함께 삭제됩니다.

`node scripts/test-api.mjs`로 기간·우선순위·성공 기준·예상 시간 저장, 두 번 수정 후 원본 보존, ID 유지, 오래된 수정 거절, 미실행 0분과 삭제를 확인했습니다. 종료일이 시작일보다 이르거나 성공 기준이 비어 있으면 400으로 거절됩니다. TypeScript 검사와 빌드도 통과했습니다. 브라우저에서 실제 팟캐스트 기록의 최초 버전과 수정본을 확인했습니다.

추가 마이그레이션 적용: 위 로컬 DB 명령의 파일명을 `drizzle/0001_free_patriot.sql`로 바꿔 한 번 실행합니다. 첫 마이그레이션 다음에 적용해야 합니다.

## 카드 2: 계획별 할 일

각 계획의 `할 일 추가`에서 제목, 마감일, 우선순위, 태그, 예상 시간을 입력합니다. 태그는 쉼표로 나누며 최대 10개입니다. 예상 시간을 모르면 빈칸으로 두고 ‘미정’으로 저장할 수 있습니다. `완료로 바꾸기`를 누르면 완료 상태가 되고, 같은 위치의 `진행 중으로 되돌리기`로 되돌릴 수 있습니다. 상태는 서버에 저장됩니다. 할 일을 완료해도 실제 실행 내용이나 시간을 임의로 작성하지 않습니다.

제목·태그 검색, 상태·우선순위·정확한 태그 필터를 함께 적용할 수 있습니다. 검색과 필터, 정렬은 `/api/tasks`가 D1에서 처리합니다. 기본 정렬은 마감일 빠른 순이며 우선순위, 예상 시간, 생성 시각 기준으로 변경할 수 있습니다. 같은 값이면 생성 시각 오래된 순, 그다음 ID 오름차순입니다. 예상 시간 미정은 시간 정렬에서 마지막에 나옵니다. 이 기준은 목록 위에도 표시됩니다.

`10월 생활·학습 일정`에 사용자가 제공한 분리수거, 월세 납부, 팀프로젝트, SKT ALEPH 견학, 겨울 옷 꺼내기의 다섯 할 일을 저장합니다. 태그는 각각 생활·납부·팀프로젝트·견학·생활로 정리했습니다. 4시간과 2시간은 240분과 120분이며 견학 시간은 미정입니다. 상위 계획의 예상 372분은 알려진 네 항목의 합계이고 견학 시간은 포함하지 않았습니다.

`node scripts/test-tasks.mjs`는 로컬 DB에서 검증용 할 일 다섯 개를 생성해 수정, 완료, 되돌리기, 삭제를 확인하고 테스트 계획을 정리합니다. 완료 필터는 1건에서 되돌린 뒤 0건, 진행 중은 4건에서 5건으로 바뀌었습니다. 제목·태그 검색, 상태·우선순위·태그 필터, 같은 값의 정렬 순서 유지, 미정 시간의 마지막 배치를 확인했습니다. 오래된 버전으로 덮어쓰기는 409로 거절합니다. 카드 1 회귀 검사와 TypeScript 검사도 통과했습니다.

브라우저에서도 로컬 검증용 임시 할 일을 생성·수정·완료·되돌리기한 화면과 삭제 후 화면을 보관했습니다. 실제 기록의 완료 여부와 구분하기 위해 공개 서버에 임시 검증 할 일을 넣지 않습니다. 추가 마이그레이션은 `0002_faulty_kinsey_walden.sql`, `0003_married_machine_man.sql` 순서로 적용합니다.

## 카드 3: 할 일별 실행 기록

각 할 일의 `실행 기록 남기기`에서 서울 시간 기준 시작·종료 시각, 막혔던 이유와 한 일을 입력합니다. 실제 시간은 종료에서 시작을 뺀 뒤 분 단위로 반올림합니다. 실행 기록은 별도 `executions` 테이블에 저장하며 계획의 제목·기간·예상 시간이나 할 일의 예상 시간을 바꾸지 않습니다. 여러 번 실행한 일에는 실행 기록을 여러 건 남길 수 있습니다.

실행 요청 키는 DB 기본키이며, 같은 할 일의 시작·종료 시각에도 고유 인덱스가 있습니다. 같은 키를 재전송하거나 같은 시간대의 같은 기록을 다시 저장해도 한 건만 남습니다. 같은 키나 시간대로 다른 내용을 보내면 409 오류를 표시합니다. 완료 처리도 별도 `completions` 테이블의 요청 키와 할 일 ID·변경 전 버전 고유 인덱스로 중복을 막습니다. DB 트리거가 같은 트랜잭션에서 완료 상태를 바꿉니다. 되돌리기는 실행 기록을 삭제하지 않으며, 오래된 완료 요청을 재전송해도 다시 완료로 만들지 않습니다.

사용자 제공 Velog 기록은 2026-10-14 10:00~13:00(서울), 예상 60분·실제 180분입니다. 막힌 이유는 수업 교안 이론 내용을 다시 정리하느라 오래 걸렸다는 내용으로 저장했습니다. 임의의 실행 사실은 추가하지 않았습니다.

## 카드 4: 숫자의 근거

돌아보기는 선택한 기간에 마감일이 포함된, 삭제하지 않은 할 일을 대상으로 합니다. 전체 계획 또는 특정 계획을 선택할 수 있습니다. 계획 수는 대상 할 일 수, 완료 수는 현재 완료 상태 수입니다. 지연 수는 서울 기준 오늘보다 마감일이 앞선 미완료 할 일 수이며 완료한 일은 지연에서 제외합니다. 막힘 수는 막힌 이유가 있는 실행 기록이 하나 이상 연결된 할 일 수입니다.

예상 시간은 대상 할 일의 예상 시간 합계, 실제 시간은 그 할 일에 연결된 모든 실행 기록의 시간 합계입니다. 실행 시각이 기간 밖이어도 대상 할 일에 속한 기록이면 포함합니다. 차이는 실제에서 예상을 뺀 값입니다. 미정 예상 시간은 합계에 0으로 반영하고 미정 건수를 따로 표시합니다. 대상이 없으면 모두 0입니다.

숫자를 누르면 포함된 할 일과 실행 기록이 아래 근거 목록에 표시됩니다. `할 일로 이동`을 누르면 원래 할 일로 이동합니다. 고칠 점은 출발 계획당 한 건을 다음 계획으로 연결하며, 동시에 두 번 요청해도 같은 다음 계획을 반환합니다. Velog 개선 문장은 사용자가 승인한 ‘포스팅 전에 교안 이론을 먼저 정리하고, 예상 시간을 3시간으로 잡기’이며 다음 계획 날짜는 2026-10-21, 예상 180분입니다.

추가 마이그레이션은 `0004_groovy_naoko.sql`, `0005_clumsy_lethal_legion.sql`, `0006_tearful_stone_men.sql` 순서로 적용합니다.

## 카드 5: 전체 자료 보관

첫 화면의 `전체 자료 내보내기`는 `/api/export`에서 D1의 여섯 표를 하나의 batch 읽기로 가져와 JSON 파일로 반환합니다. 계획·수정 이력·할 일·실행·완료 이력·다음 계획 연결과 같은 시점 자료로 계산한 전체 기간 돌아보기를 포함합니다. 원본 JSON 문자열 필드인 태그와 계획 스냅샷도 그대로 보관합니다. `formatVersion: 2`, 서울 표시 시간대, 분 단위 정보와 DB 계약을 파일 안에 포함합니다. 가져오기 기능은 없습니다.

`contracts/pds-schema-v2.json`에 DB 열 이름과 API 필드 이름, nullable 여부, 관계의 실제 강제 방식, 고유 제약, 트리거, 날짜·단위·집계 규칙을 기록했습니다. 시간 없는 날짜는 변환하지 않고 실행 시각은 서울 입력을 UTC로 저장해 서울로 표시합니다.

`node scripts/test-export.mjs`는 반복 다운로드의 원본 자료가 같은지, 서버와 ID·날짜·예상 시간·상태·실행 ID가 일치하는지 검사합니다. `scripts/audit-secrets.py`는 소스·배포 빌드·소스 ZIP·모든 도달 가능한 Git blob에 알려진 비밀키 형식과 개인키 헤더가 있는지 검사합니다. 임의의 모든 비밀값 형식을 탐지한다는 뜻은 아닙니다.

로컬 DB에 `<script>` 모양 제목을 저장한 뒤 실제 브라우저에서 글자 그대로 표시되는지 확인했습니다. DOM에 해당 실행용 script 노드는 없었고, 스크립트가 실행됐을 때만 생기는 data-pds-xss 속성도 없었습니다. 콘솔 경고·오류는 없었습니다. 검증용 계획은 확인 후 삭제했고 실제 사용자 기록 수에 포함하지 않습니다.

## 카드 5 검증 결과와 범위

로컬 내보내기 검사에서 실행 기록 세 건과 완료 이력 세 건을 확인했습니다. 반복 다운로드와 서버 재조회에서 ID·날짜·분 단위 값이 일치했습니다. 스크립트 모양 제목은 실행되지 않고 그대로 보였으며 DOM 실행 표식과 해당 script 노드가 없었습니다. 해당 로컬 화면의 콘솔 경고·오류 목록은 비어 있었습니다.

소스·빌드·소스 ZIP·도달 가능한 Git blob을 비밀키 패턴과 개인키 헤더로 검사해 일치 항목이 없었습니다. 이는 알려진 형식에 대한 검사이며 임의의 모든 비밀값 형식을 탐지했다는 뜻은 아닙니다. 공개 서버의 응답 검사 결과는 별도 증거 파일에 보관합니다.

새 시크릿 창 UI 검증은 Windows 컴퓨터 사용 도구가 현재 브라우저 URL을 확인하지 못해 중단됐습니다. 따라서 T06-C01의 ‘새 시크릿 창’ 조건은 자동 검증 완료로 표시하지 않습니다. 쿠키·인증 헤더 없는 HTTP 요청으로 결과물·소스·JSON 다운로드가 열리는지는 별도로 검사합니다.
